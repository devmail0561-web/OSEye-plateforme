## Configuration Method

The OSEye agent is configured exclusively through environment variables. The systemd service loads them from `/etc/oseye/agent.env`.

The `oseye-config` CLI tool provides safe management of these values with validation, atomic writes, and file locking.

## Using oseye-config

```bash
# Show current effective configuration
sudo oseye-config show

# Validate all settings
sudo oseye-config validate

# Set a value (validated before write)
sudo oseye-config set OSEYE_GRPC_ADDR=server.prod:50051

# Get a specific value
sudo oseye-config get OSEYE_BATCH_SIZE

# Remove a key (reverts to default)
sudo oseye-config unset OSEYE_BATCH_SIZE

# Check that referenced files (certs, keys) exist
sudo oseye-config check-files

# Show env file path in use
sudo oseye-config env-file
```

## Environment Variables

### Connection

| Variable | Default | Description |
|----------|---------|-------------|
| `OSEYE_GRPC_ADDR` | `localhost:50051` | Server gRPC address (host:port) |
| `OSEYE_TLS_CERT` | — | Path to agent TLS certificate |
| `OSEYE_TLS_KEY` | — | Path to agent TLS private key |
| `OSEYE_TLS_CA` | — | Path to CA certificate |
| `OSEYE_ENROLL_URL` | — | Auto-enrollment server URL (https only) |
| `OSEYE_ENROLL_TOKEN` | — | One-time enrollment token |

### Identity

| Variable | Default | Description |
|----------|---------|-------------|
| `OSEYE_AGENT_ID` | auto-generated | Agent UUID v4 identifier |

### Performance

| Variable | Default | Description |
|----------|---------|-------------|
| `OSEYE_BATCH_SIZE` | `1000` | Events per batch (1–100000) |
| `OSEYE_BATCH_TIMEOUT_MS` | `1000` | Max wait before sending batch (ms) |
| `OSEYE_MAX_CPU_PCT` | `4.0` | CPU usage limit (0–100) |
| `OSEYE_MAX_MEM_MB` | `256` | Memory usage limit in MB |

### Storage

| Variable | Default | Description |
|----------|---------|-------------|
| `OSEYE_BUFFER_PATH` | `/var/lib/oseye/buffer.db` | Offline buffer SQLite path |
| `OSEYE_QUARANTINE_DIR` | `/var/lib/oseye/quarantine` | Quarantined files directory |

### Crypto

| Variable | Default | Description |
|----------|---------|-------------|
| `OSEYE_ED25519_SIGNING_KEY` | `/etc/oseye/certs/agent.ed25519.key` | Ed25519 batch signing key |

### Collection

| Variable | Default | Description |
|----------|---------|-------------|
| `OSEYE_FANOTIFY_PATHS` | `/` | Comma-separated absolute paths for fanotify |
| `OSEYE_INOTIFY_WATCHES` | — | JSON array of inotify watch configs |
| `OSEYE_JOURNALD_PRIORITY` | `warning` | Minimum journald priority |
| `OSEYE_JOURNALD_UNITS` | — | Comma-separated systemd units to watch |
| `OSEYE_SYSLOG_ADDR` | `127.0.0.1:514` | Syslog listener address (host:port) |

## Validation Rules

All values are strictly validated at startup:

- **Ports**: numeric, range 1–65535
- **Paths**: must be absolute (`/...`)
- **Agent ID**: must be valid UUID v4 (if set)
- **Batch size**: must be 1–100000
- **CPU percent**: must be 0–100
- **Memory MB**: must be > 0
- **Quarantine dir**: cannot be a critical path (`/`, `/etc`, `/usr`, etc.)
- **Enroll URL**: must use `http://` or `https://` scheme

## Secrets Management

### Development (local)

For local development, use the `.env` file approach:

```bash
# Copy the example files
sudo cp packaging/config/server.env.example /etc/oseye/server.env
sudo cp packaging/config/secrets.env.example /etc/oseye/secrets.env
sudo chmod 600 /etc/oseye/secrets.env
```

### Production with Docker Secrets

The `docker-compose.prod.yml` uses Docker secrets for sensitive values:

```yaml
secrets:
  db_password:
    file: /etc/oseye/db_password.txt
```

### Production with HashiCorp Vault

For enterprise deployments, integrate with Vault for automatic secret rotation:

```bash
# Store secrets in Vault
vault kv put secret/oseye/server \
  db_password="$(openssl rand -hex 16)" \
  admin_password="$(openssl rand -base64 24)" \
  jwt_private_key=@/etc/oseye/certs/jwt_private.pem

# Agent-side: use vault-agent sidecar to template agent.env
# /etc/vault-agent.d/oseye.hcl
template {
  source      = "/etc/vault-agent.d/agent.env.ctmpl"
  destination = "/etc/oseye/agent.env"
  perms       = 0600
  command     = "systemctl restart oseye-agent"
}
```

Example Vault template for agent.env:
```bash
# /etc/vault-agent.d/agent.env.ctmpl
{{ with secret "secret/oseye/agent" }}
OSEYE_GRPC_ADDR={{ .Data.data.grpc_addr }}
OSEYE_ENROLL_TOKEN={{ .Data.data.enroll_token }}
{{ end }}
```

### Production with AWS Secrets Manager / GCP Secret Manager

Reference secrets via environment variables pointing to the secret ARN/path, then use an init container or entrypoint script to resolve them before starting the service.

## Server Configuration

Run the interactive setup wizard after installation — it writes both config files for you:

```bash
sudo oseye-server setup
```

The wizard generates:
- `/etc/oseye/server.env` (mode 640) — non-sensitive settings
- `/etc/oseye/secrets.env` (mode 600) — credentials and secrets

For PostgreSQL, `OSEYE_DB_URL` (which contains the password) is written **only** to `secrets.env`. `server.env` contains only the non-sensitive DB settings (`OSEYE_DB_BACKEND`, pool sizes).

Key server variables:

```bash
# server.env
OSEYE_DB_BACKEND=postgresql
OSEYE_REDIS_URL=redis://redis:6379/0
OSEYE_GRPC_PORT=50051
OSEYE_API_PORT=8000
OSEYE_ENV=production  # Disables API docs, enforces strong passwords

# secrets.env (mode 600)
OSEYE_DB_URL=postgresql+asyncpg://oseye:PASSWORD@postgres:5432/oseye
OSEYE_SECRET_KEY=<hex-32-bytes>
OSEYE_ADMIN_PASSWORD=<strong-password>
```

Use `oseye-config` on the agent side for validated configuration. For the server, edit `/etc/oseye/server.env` and `/etc/oseye/secrets.env` directly or use Docker environment injection. Full reference: [Server Configuration](/OSEye-plateforme/reference/config-server/).

## Surveillance Profiles

The server pushes a surveillance profile to each agent. Available profiles:

| Profile | Description |
|---------|-------------|
| `workstation` | Standard desktop monitoring |
| `server` | Production server (full collectors) |
| `investigation` | Deep monitoring (all events, no throttle) |
| `minimal` | Reduced collection for low-resource systems |
| `compliance` | Focused on audit/compliance events |
| `stealth` | Minimal footprint, reduced logging |
