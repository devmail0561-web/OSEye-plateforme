## Architecture

On Kubernetes, OSEye deploys as:

- **DaemonSet**: `oseye-agent` on every node (privileged, host PID/network)
- **Deployment**: `oseye-server` (2+ replicas, stateless)
- **Deployment**: `oseye-workers` (scaled per type)
- **StatefulSet**: PostgreSQL (or use a managed DB)
- **StatefulSet**: Redis (or use managed Redis)
- **Ingress**: Dashboard + API access

## Planned Helm Values

```yaml
# values.yaml (target)
agent:
  image: ghcr.io/oseye/oseye/oseye-agent
  resources:
    limits:
      cpu: 200m
      memory: 256Mi
  tolerations:
    - operator: Exists

server:
  replicas: 3
  image: ghcr.io/oseye/oseye/oseye-server
  resources:
    limits:
      cpu: "1"
      memory: 2Gi

workers:
  types: [normalizer, rule_engine, ml_engine, ti_engine, correlator]
  replicas: 2

database:
  external: true
  url: postgresql://oseye:password@pg-cluster/oseye

redis:
  external: true
  url: redis://redis-cluster:6379/0

ingress:
  enabled: true
  host: oseye.example.com
  tls: true
```

## Security Considerations

- Agent runs as privileged DaemonSet (required for eBPF/fanotify)
- Use Kubernetes secrets for TLS certificates and tokens
- Network policies to restrict agent-to-server communication
- PodSecurityPolicy/Standards for server and worker pods
- mTLS between all components via cert-manager
