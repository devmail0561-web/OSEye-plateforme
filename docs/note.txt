## Commandes de développement (Makefile)

Depuis la racine du projet :

    make setup      — vérifier que l'environnement est prêt (Go + Python + protoc)
    make proto      — régénérer les stubs Go et Python depuis proto/event.proto
    make test       — tous les tests (Go + Python)
    make test-go    — go test -race ./...
    make test-py    — pytest server/tests/ -v
    make lint       — ruff (Python) + go vet (Go)
    make audit      — scanner de sécurité interne (tools/audit/)
    make dev-up          — démarrer Redis + Postgres via Docker Compose
    make dev-down        — arrêter les services Docker
    make dev-certs       — générer le PKI dev (CA + server + agent-dev + JWT) dans infra/certs/
    make run-server      — lancer le serveur FastAPI + gRPC en local (SQLite, insecure)
    make run-server-mtls — lancer le serveur avec mTLS (requiert make dev-certs)
    make run-workers     — lancer les workers background (normalizer + storage_writer)
    make run-agent       — lancer l'agent en local (procfs, buffer SQLite, sans certs)
    make run-agent-mtls  — lancer l'agent avec mTLS (requiert make dev-certs)

Tests d'interaction (depuis server/) :
    pytest tests/integration/              — interaction modules (bus, normalizer, storage, API)
    pytest tests/integration/test_grpc_*   — communication gRPC réelle mTLS (PKI in-memory)
    pytest tests/scenarios/                — scénarios bout-en-bout (agent→gRPC→bus→DB→API)
    pytest tests/                          — toute la suite (97 tests)

Prérequis installés :
    Go 1.23.8       → ~/go/bin/go
    Python 3.12     → .venv/bin/python3.12  (venv à la racine du projet)
    protoc 29.3     → ~/.local/bin/protoc
    Activer le venv : source .venv/bin/activate

Le **Decision Engine** est celui qui décide :
 
* faut-il alerter ?
* faut-il ignorer ?
* faut-il augmenter le niveau de surveillance ?
* faut-il lancer une investigation ?
* faut-il isoler le processus ?
* faut-il demander une validation humaine ?
 
Ainsi OSEye ne devient pas seulement un observateur, mais un système capable de prendre des décisions cohérentes à partir de plusieurs sources d'information.

### Ma recommandation
 
Avant d'ajouter toutes ces fonctionnalités, je transformerais ton cahier des charges en un **document d'architecture (Software Architecture Document)** de 50 à 80 pages. Il inclurait les exigences fonctionnelles, les exigences non fonctionnelles, les composants, les diagrammes (C4, UML, séquences), les flux d'événements, les interfaces entre modules, le modèle de données et la feuille de route. Ce document deviendrait la référence unique du projet et faciliterait le développement, les tests et l'arrivée de nouveaux contributeurs.
