## Critique (à corriger en priorité)

### A-1 — `nft flush chain` efface TOUS les blocages actifs
**Fichier :** `agent/internal/responder/executor.go` — `UnblockIP()`  
**Problème :** `nft flush chain inet oseye output` supprime **toutes** les règles de la chaîne, pas uniquement la règle ciblant l'IP passée en paramètre. Déverrouiller une IP efface silencieusement tous les autres blocages en cours.  
**Correction :** stocker le handle de règle retourné par `nft add rule ... -e` dans `ActionState.Payload["nft_handle"]` lors de `BlockIP`, puis appeler `nft delete rule inet oseye output handle <N>` dans `UnblockIP`.  
**Priorité :** CRITIQUE — impact sur l'intégrité du Response Engine en production.

---

### A-2 — Enrollment : pas de validation du certificat reçu
**Fichier :** `agent/internal/enrollment/client.go` — `signCSR()`  
**Problème :** le certificat signé retourné par le serveur est écrit sur disque sans vérification :
- Le CN du cert n'est pas comparé au hostname fourni
- La signature du cert par la CA téléchargée n'est pas vérifiée
- Si `EnrollURL` est en HTTP (pas HTTPS), le token, la clé privée RSA et le cert transitent en clair  
**Correction :**
1. Parser le cert PEM reçu avec `x509.ParseCertificate` et vérifier que `cert.Subject.CommonName == hostname`
2. Vérifier la signature : `cert.CheckSignatureFrom(caCert)`
3. Logguer un warning si `EnrollURL` ne commence pas par `https://`  
**Priorité :** ÉLEVÉE — un serveur compromis ou un MITM peut injecter un faux certificat.

---

### A-3 — Race condition sur upsert `AgentRow`
**Fichier :** `server/oseye/storage/repositories/agents.py` — `upsert()`  
**Problème :** le pattern `get()` → `add()` ou mutation → `commit()` n'est pas atomique. Deux connexions simultanées du même agent peuvent provoquer un `IntegrityError` (violation de PRIMARY KEY sur `cn`). L'erreur est absorbée silencieusement par `run_coroutine_threadsafe`.  
**Correction :** remplacer par un `INSERT OR REPLACE INTO` via SQLAlchemy `insert(...).on_conflict_do_update(...)`.  
**Priorité :** ÉLEVÉE en production avec beaucoup d'agents, faible en dev (SQLite sérialise).

## Élevée

### A-4 — `ml_engine.learn_from_alert` bloque la boucle asyncio
**Fichier :** `server/oseye/api/routers/alerts.py` — `mark_false_positive()`  
**Problème :** l'appel `ml_engine.learn_from_alert(trigger_event, [])` est synchrone et s'exécute dans une coroutine FastAPI. Si le calcul est long (mise à jour LogisticRegression sur beaucoup de techniques), il bloque la boucle événementielle et dégrade la latence de tous les endpoints.  
**Correction :** wraper dans `asyncio.get_event_loop().run_in_executor(None, ...)` pour le déléguer au thread pool.  
**Priorité :** ÉLEVÉE si le parc d'alertes grossit.

---

### A-5 — Même problème dans `rule_worker.py`
**Fichier :** `server/oseye/workers/rule_worker.py` — `_create_alert()`  
**Problème :** `self._ml_engine.learn_from_alert(event, list(match.mitre))` est appelé **avant** la publication sur `alerts:created`. Si l'appel ML est lent, il retarde la propagation de l'alerte vers le CorrelationWorker.  
**Correction :** déplacer l'appel ML **après** la publication sur `alerts:created`, et l'encapsuler dans `run_in_executor`.

---

### A-6 — Token d'enrollment exposable via proxy HTTP
**Fichier :** `agent/internal/enrollment/client.go`  
**Problème :** le token est intégré dans l'URL (`/api/v1/enroll/{token}`). Tout proxy, load balancer ou système de logging qui capture les URLs sortantes expose le token.  
**Correction :** passer le token dans un header HTTP (`X-Enroll-Token`) plutôt que dans le path. Nécessite une modification du router serveur correspondant.

## Moyenne

### A-7 — `nowNs()` dupliqué entre deux packages Go
**Fichiers :** `agent/internal/commands/client.go:296` et `agent/internal/responder/state.go:134`  
**Problème :** fonction identique définie deux fois dans deux packages différents.  
**Correction :** exporter `NowNs()` depuis `responder` ou créer un package `internal/clock` partagé.

---

### A-8 — ISOLATE sans `dst_ip` ne remonte pas d'alerte opérationnelle
**Fichier :** `server/oseye/decision/action_executor.py` — `_emit_block_ip_command()`  
**Problème :** si l'alerte n'a pas de `dst_ip`, le BLOCK_IP est skippé avec un simple `log.info`. L'opérateur ne voit rien — la décision ISOLATE est produite mais l'action correspondante n'est pas exécutée, sans notification.  
**Correction :** publier un événement sur `notifications:pending` ou sur `decisions:completed` avec un champ `action_skipped_reason: "no_dst_ip"` pour que le dashboard puisse afficher un warning.

---

### A-9 — Race condition UI : création de clé API vs rechargement initial
**Fichier :** `ui/src/pages/admin/ApiKeys.tsx`  
**Problème :** si `load()` (GET initial) répond après `handleCreate` (POST), le `setKeys(data.items)` écrase la nouvelle clé ajoutée localement au state. La clé disparaît de la liste jusqu'au prochain rechargement.  
**Correction :** annuler le `load()` en cours si `handleCreate` démarre (via `AbortController`), ou attendre que `creating === false` avant de lancer le GET initial.

---

### A-10 — Erreur 413 plugin upload non explicite
**Fichier :** `ui/src/pages/admin/Plugins.tsx` — `handleUpload()`  
**Problème :** une erreur HTTP 413 (fichier > 1 Mo) affiche "Erreur lors de l'installation" sans indiquer la cause.  
**Correction :**
```typescript
const status = (err as { response?: { status?: number } })?.response?.status
if (status === 413) setUploadError('Fichier trop grand (max 1 Mo)')
```

## Faible

### A-11 — `ReportActions` : `fut.result(timeout=2.0)` bloque le thread gRPC
**Fichier :** `server/oseye/ingest/grpc_service.py` — `ReportActions()`  
**Problème :** sur erreur DB, le thread gRPC est bloqué 2 secondes. Acceptable en fonctionnement normal mais mesurable sous haute charge (beaucoup d'agents qui reportent simultanément).  
**Correction :** timeout configurable via `Settings.agent_report_db_timeout_s`.

---

### A-12 — État sidebar non persisté entre sessions
**Fichier :** `ui/src/components/layout/Sidebar.tsx`  
**Problème :** `useState(false)` — la sidebar repart dépliée à chaque rechargement de page.  
**Correction :** initialiser depuis `localStorage.getItem('sidebar_collapsed')` et persister à chaque toggle.
